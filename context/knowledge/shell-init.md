# Shell initialization and shared functions

- Source: `home/.profile`, `home/.shrc`, `home/.bash_profile`, `home/.bashrc`, `home/.zprofile`, `home/.zshrc`, and `home/.config/{shell,bash,zsh}/`
- Why it matters: controls PATH, prompt, aliases, and the shared shell baseline.
- When to consult: changing shell startup order, adding shared shell helpers, or deciding whether behavior belongs in POSIX baseline vs shell-specific layers.
- Key points: `.profile` and `.shrc` bootstrap into `shell/profile.sh` and `shell/rc.sh`, which in turn source `shell/paths.sh` to export default `XDG_*` vars and derive the shell's unexported internal `dotfiles_*` path layer. Bash and zsh each have profile/rc wrappers that layer their shell-specific config on top. The shared login profile now runs a guarded Homebrew bootstrap (`brew shellenv`) when Homebrew exists at `/opt/homebrew/bin/brew` or `/usr/local/bin/brew`; after that, `~/.local/bin` and `~/bin` are still prepended so user-local tools win. `make-chrome-app` lives in `~/.local/bin/`. Shell-language policy is now explicit: use POSIX `sh` for deployment-critical bootstrap/shared runtime baselines, `bash` for repo-local dev automation like `scripts/verify.sh`, and `zsh` for interactive prompt/completion UX. Zsh now initializes `compinit`, picks up the managed `_git` completion file from the resolved zsh config home, and sources `prompt.zsh` for a zsh-native prompt that mirrors the bash layout (user/host, cwd, git state, history number, conditional jobs count). The intended boundary is “shared policy/helpers in `shell/`, shell-native interactive internals in `bash/` and `zsh/`,” not a shared abstraction over prompt/completion hooks.
- Gotchas: the shell entrypoints intentionally remain in `$HOME` for compatibility, even though the managed internals now prefer XDG-derived paths. Bash and zsh history now live under `XDG_STATE_HOME` / `~/.local/state` unless explicitly overridden. Prefer the internal `dotfiles_*` vars for shell path plumbing after `paths.sh` has loaded, and reserve raw `XDG_*` fallback logic for the tiny wrapper/bootstrap edge. `paths.sh` is now required infrastructure rather than a best-effort helper: the shared and shell-specific rc/profile layers fail fast if it cannot be loaded or does not initialize the expected path vars. The repo no longer supports repo-managed shell-local override hooks like `profile.local.sh`, `local.sh`, `local.bash`, or `local.zsh`, but the home-level `_local` files remain supported as the host-specific override layer: `.profile_local`, `.sh_local`, `.bash_profile_local`, `.bash_local`, `.zprofile_local`, and `.zsh_local`. Shell files under `home/.config/bash/` and `home/.config/zsh/` are intended for their target shell only; `lib/git` is vendored, and the managed git helper files under `~/.config/{bash,zsh}/` are real symlink nodes in `home/.config/{bash,zsh}/` that point into that vendor tree so `git pull` and submodule updates flow through immediately. Most of the shell stack is now meant to be rerunnable in the same shell: `paths.sh`, `rc.sh`, `bash/rc.bash`, `zsh/rc.zsh`, and `zsh/prompt.zsh` no longer use coarse file-level guards, and the zsh layer dedupes `fpath` / `precmd` registration instead. The old `DOTFILES_*_LOADED` markers were removed entirely once they stopped serving a real runtime purpose. The remaining narrow guard is Homebrew `shellenv` inside `home/.config/shell/profile.sh`, because rerunning that block would otherwise duplicate PATH-like entries; that guard still uses a process-local token (`${BASHPID:-$$}` / `$$`) so inherited stale env from a parent GUI/session does not block startup. `home/.vim` is also a real symlink node, pointing to `../managed/vim` for the whole-directory Vim case. Do not assume zsh is automatically the best scripting language here; for mostly-orchestration scripts, bash remains the default unless there is a specific zsh-only payoff.
